## What was done

**Asked:** "Time in log is still wrong. I am +10GMT AEST. It is 2151....the
log is saying 12."

**Found:** the activity log's displayed time (`renderLog()` in
`app/templates/index.html`) was still pinned to a fixed IANA timezone from
an earlier fix — first `UTC`, then `Europe/London` (see
[260823_1147_activityLogTimezone.md](260823_1147_activityLogTimezone.md)).
Neither matches Brad's actual timezone, AEST (UTC+10).

Asked Brad which Australian IANA zone to pin to, since this is the same
class of bug as the `Europe/London` fix (a fixed zone drifts once DST
kicks in for that region) — needed to know whether he's in a state that
observes daylight saving (NSW/VIC/TAS, which shift to AEDT/+11 in October)
or one that doesn't (QLD, always AEST/+10). He confirmed **Australia/Brisbane**
(Queensland, no DST).

**Fix:** changed `timeZone: 'Europe/London'` to `timeZone:
'Australia/Brisbane'` in the `toLocaleTimeString()` call in `renderLog()`.
Brisbane stays at AEST year-round, so this won't drift again in October
the way the London pin drifted when BST started.

**Outcome:** fixed and deployed (dashboard restarted via
`POST /api/admin/restart` on port 8420 — the earlier attempt at port 5000
was wrong, dashboard actually listens on 8420) and verified live via
`curl` that the rendered page now carries `timeZone: 'Australia/Brisbane'`.
Committed and pushed.
