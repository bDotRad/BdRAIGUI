Help for Retards

Right boet, here's the whole thing in small words. No jargon. Read it once, you'll get it.

1. The servers (the computers)

A "server" is just a computer that stays on all the time so other people can reach it. Brad has a few:

BdRSrvDev — the "dev" (development) machine. This is the workbench. All the building and fixing happens here. The dashboard you're looking at right now runs on this one.

BdRPiAMI — a little Raspberry Pi (tiny cheap computer) that runs the finished apps so real users can use them.

BdRBirdDetector — another Pi that does one job: watching birds.

A couple more are planned but don't physically exist yet.

TL;DR: one computer to build on, other computers to run the finished stuff on.

2. The DEV application (this dashboard)

The thing you're clicking around in is called BdRDev. It's a control panel. Two jobs:

a) Show every project Brad is working on and let him drop in new jobs ("requests").

b) Run a scheduler — a timer that takes turns waking up each project, letting a robot assistant do the outstanding work, then putting it back to sleep. Round-robin, like taking turns.

TL;DR: it's the foreman. It hands out jobs and keeps the crew rotating.

3. Project folders + READY / Waiting Input

Every project is just a folder on the dev machine. Inside each one is a folder called _Requests — that's the in-tray. You want something done, you drop a note in the in-tray.

Each note has a status written at the top:

NOT READY — "I'm still writing this, don't touch it yet."

READY — "Go. Do this now." The scheduler will pick it up next time it wakes that project.

WAITING RESPONSE ("Waiting Input" on the dashboard) — the robot started the job, got stuck, and needs Brad to answer a question before it can carry on. Nothing happens until Brad replies and flips it back to READY.

When a job's done, the note gets moved into an _Archive folder with a write-up of what happened, so there's a paper trail.

TL;DR: leave a note in the in-tray, mark it READY, wait. If it says Waiting Input, the robot needs you.

4. GitHub — push and pull

GitHub is an website in the cloud that keeps the master copy of every project's code, plus its full history (every change ever, who made it, when).

Push = "upload my latest changes to the master copy." You do this after finishing work.

Pull = "download the latest master copy onto this machine." You do this before starting work, or to update a server with the newest code.

Rule here: real changes are only ever made on the dev machine and pushed from there. The other servers are pull-only — they just download, they never upload. Keeps things tidy and stops two machines fighting over what's correct.

TL;DR: push = save to the cloud. pull = get the latest from the cloud. Only the dev machine pushes.

5. How the apps run on the servers

Once an app is built and tested on the dev machine, it gets deployed (installed and switched on) on one of the other servers — usually the Pi.

The steps are always: build on dev → push to GitHub → the server does a pull to grab it → the app restarts on the server with the new code.

On the server the app runs as a service — meaning the computer keeps it running automatically and restarts it if it falls over, without anyone logging in. Each app has its own web address (an IP number, sometimes a proper URL) so users can open it in a browser.

If someone has to tweak something directly on a live server in an emergency, they don't push from there. They copy the changed file back to the dev machine, leave a request, and let the normal process fold it in properly.

TL;DR: build on dev, ship to the server via GitHub, the server runs it as a background service on its own address.

6. How the Claude robots (agents & sessions) work

Claude is an AI. Claude Code is Claude wired into a computer so it can actually read files, write code, run commands — do the work, not just chat about it.

A session is one running copy of that robot, parked in one project's folder. The scheduler starts a session when a project has READY work, and stops it when there's nothing left to do. Each project gets its own session; they don't share.

An agent is a specialist the main session can call in for a specific kind of job. Think of the session as a general contractor who phones a subbie:

• Project Manager — reads the in-tray, works out what each job needs, hands it to the right specialist.
• Web Dev Expert — writes the actual app code.
• Supabase SQL Expert — handles the database (where the app's data is stored).
• Doc Updater — keeps the written instructions in step with reality.

There's also one permanent Independent Claude session that never sleeps. Its job is to keep an eye on all the other sessions and answer Brad directly if he asks something that isn't tied to one project.

TL;DR: a session is one robot working one project. Agents are specialist robots it calls in. The scheduler switches them on and off.

The whole loop, in one breath

Brad drops a note in a project's in-tray and marks it READY → the scheduler wakes a Claude session in that project → the session (with help from its specialist agents) does the work on the dev machine → it commits and pushes the result to GitHub → the live server pulls it down and restarts the app → the session archives the note and goes back to sleep. Then it's the next project's turn.
